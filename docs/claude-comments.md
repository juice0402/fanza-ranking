# Claude によるコメントの仕上げ（毎日の予約タスク）

サイトの作品ごとの「ひとことコメント」は、2段階で作ります。

1. **毎日 0:05（日本時間）**: 自動更新（`get_new_releases.py`）で、Gemini が**下書き**を書く（`comment_kind: "ai"`）。
   Gemini の無料枠（1日20回ほど）を使い切ったときや、答えに確かめられない評価（「待望」「話題」など。`HYPE_WORDS`）・使えない言葉が入っていたときは、作品情報から作った**定型文**（`comment_kind: "template"`）になる
2. **毎日 0:20（日本時間）**: Claude の予約タスクが、下書きと定型文を読み直して、**完成した文章に書き上げる**（`comment_kind: "claude"`）

この手順書は、2 の予約タスクのためのものです（予約タスクはこの手順書どおりに動きます）。

書き上げる対象は7つです（`list` の `reason` で分かります）。
- **Gemini の下書き**のままの作品（`reason: 下書きを仕上げる`。`draft` に下書きが入る）
- **定型文のまま**の作品（`reason: 定型文`）
- **発売日をすぎたのに、コメントに「予約」「発売予定」「発売前」などの言い方が残っている**作品（`reason: 予約の言い方が残っている`。仕上げ済みのものも含む）。予約中に書いたコメントが、発売後も「予約受付中」のままにならないようにするため。「発売されます」「出ます」「控えています」のような、これから先のことを言う言い方も同じ（予約のうちに書いたコメントは、発売日をすぎると書き直しの対象になる。そのころには収録時間・ジャンル・サンプルも増えているので、その情報も入れて書き直す）
- **仕上げたあとに出演者が載った**作品（`reason: 出演者が載った`）: 予約のうちは出演者が空で、あとからFANZAが載せることがある。コメントに出演者の名前が1人も入っていなければ（「出演者名は載っていません」と書いたままなど）、書き直す
- **仕上げたあとに情報が増えた**作品（`reason: 情報が増えた`）: 収録時間やジャンルが加わって「事実が少ない作品」でなくなったのに、コメントが短いまま（80文字台）なら、増えた情報を入れて書き直す
- **過去作品**（`reason: 過去作品`・`catalog: true`）: 毎日の更新が FANZAの人気順に集めている発売済みの作品（`site/src/data/catalog/YYYY-MM.json`）で、コメントがまだ無いもの。上の5つを先に出し、40件の枠が余ったら、**FANZAの人気順の順位が上の作品から**（全体の人気順と新着の人気順の、上のほう）出る（質の高い作品から書く。順位そのものは出さないし、コメントにも書かない）。**コメントが付くまで、その作品ページは検索エンジンに出ない**（noindex）ので、書くとページが検索に出るようになる。書き方は同じ（発売済みの作品として書く）
- **FANZA同人・FANZAゲーム**（`reason: 同人` / `ゲーム`・`floor: doujin` / `game`。2026-10-09 から）: 毎日の更新が FANZAの人気順に集めている同人（1,000本・`site/src/data/doujin.json`）・PCゲーム（500本＋予約・`game.json`）で、コメントがまだ無いもの。**1日40件のうち、同人4件・ゲーム1件**（運営者の希望「動画35本・同人4本・ゲーム1本」。`list --limit 40` が、いつもこの割合で出す。対象が足りない日は、残りを動画に回す）。人気順の順位が上の作品から。書き方は下の「同人・ゲームの書き方」。コメントが付くまで、その作品ページは検索エンジンに出ない

```
 0:05  GitHub Actions（get_new_releases.py）… 新作を取得 → Gemini が下書き（書けなかった作品は定型文）→ 公開
 0:20  Claude の予約タスク … （0:05 の更新が遅れていたら、先に更新を動かして待つ）→ 下書き・定型文を、Claude が書き上げる → PR → CIが緑ならMerge → 公開（GitHub Actions の Deploy。10〜15分。下書きが出ているのは30分ほど）
```

Claude が書き上げたコメントは `comment_kind: "claude"` にします（画面ではGeminiの下書きと同じ見た目。フッターの「ひとことコメントは…自動で作成」の注記の対象）。書き込んだ作品の `updated`（更新日。sitemap の `lastmod` に使う）は、`apply` が今日の日付に自動で更新します。
仕上げ済み（`claude`）の作品は上書きしません（上の「予約の言い方が残っている」ものだけ、書き直せます）。発売日がFANZAで変わったとき、コメントに古い日付が書いてあれば、毎日の更新が定型文に戻すので、その日のうちに書き直されます。

予約タスクの名前は「毎日のAIコメント書き足し（Claude）」です（実行は自動承認の設定）。予約タスクもふだんのチャットと同じClaudeの利用枠を使います。止める・時間を変える・手順を変えるときは、Claudeに頼んでください（手順そのものは、予約タスクが毎回このファイルを読むので、このファイルを直せば反映されます）。

## 手順

1. リポジトリ `juice0402/fanza-ranking` を使える状態にする（無ければ add_repo → clone）。`main` を最新にして、作業用のブランチを作る
   `git fetch origin main && git checkout -B claude/comments-$(TZ=Asia/Tokyo date +%Y%m%d-%H%M) origin/main`（ブランチ名に時刻まで入れる。同じ日にやり直したとき、前の名前のブランチが残っていても、ぶつからないように。GitHub のブランチは Claude の環境からは消せない）
   - **今日の更新（0:05）が済んでいるかを確かめる**: `bash scripts/already_updated.sh origin/main`（GitHub の定時実行は、混んでいると数時間遅れることがある。2026-10-04 は 0:05 の予定が 3:58 に動いた）
     - 「済んでいます」なら、そのまま手順2へ
     - 「まだです」なら、更新が動いている最中かを見る: `gh api "repos/juice0402/fanza-ranking/actions/workflows/update.yml/runs?per_page=3" --jq '.workflow_runs[] | .status + " " + .created_at'`。`queued` か `in_progress` があれば、それが終わるのを待つ。無ければ、更新を動かす: `gh api -X POST repos/juice0402/fanza-ranking/actions/workflows/update.yml/dispatches -f ref=main`（遅れて来た定時実行は、更新が済んでいるのを見て何もしないので、二重にはならない）
     - 30秒ごとに様子を見て、終わったら（`completed`）、もう一度 `git fetch origin main && git rebase origin/main`（まだ何も書いていなければ `git reset --hard origin/main` でもよい）で取り込み直す。20分たっても終わらない・失敗したときは、いまのデータのまま続けて、報告に書く
2. 対象を出す: `python3 scripts/claude_comments.py list --limit 40`
   - `total_pending` が 0 なら、**何も変更せず、PRも作らずに終了**（「対象なし」と報告）。過去作品が集まってくると、ほぼ毎日、枠（40件）いっぱいまで出る（`catalog_pending` は、コメントがまだ無い過去作品の数）
   - **1日に書くのは40件まで**（多い日は、残りを次の日に回す。急がなくてよい。list で40件を書き終えたら、もう一度 list しない。`apply` も、その日に仕上げた件数を数えて、40件をこえる分は断る）
   - 出るのは、出演者・メーカー・形式（VR / 8K のような英数字のタグだけ）・発売日・収録時間・シリーズとレーベル（あれば）・ジャンル（決めた一覧にあるものだけ）・サンプル動画の有無・サンプル画像の枚数・下書き（`draft`）と、安全チェックを通ったタイトル（`title`。通らなければ `title_hidden: true`。未成年を連想させるタイトルなら、さらに `content_off: true`）と、その作品の文字数の下限（`min_len`。ふつうは100、書ける事実が少ない作品は80）です
   - 同人・ゲームの作品（`floor` があるもの。いつも最後に出る）は、サークル（`circle`。同人）・ブランド（`brand`。ゲーム）・作家（`authors`。ゲーム）・シリーズ・発売日・ジャンル（おだやかなものだけ）・サンプル画像の枚数・タイトルが出る（`doujin_pending`・`game_pending` は、コメントがまだ無い本数）
3. 下の「書き方」に沿って、作品ごとにコメントを書き、`{"cid": "コメント", ...}` のJSONファイルにする（作業用の置き場に。リポジトリには入れない）
4. 点検して書き込む: `python3 scripts/claude_comments.py apply ファイル.json`
   - 先に `--dry-run` で点検してもよい。問題があると**何も書き込まれず**、理由が出る。直してもう一度実行する
   - 警告（書き出し・言い回しの偏り）が出たら、なるべく書き分けてから書き込む
5. `bash scripts/check.sh` を実行して全部成功することを確認する
6. `git status` で、変わったのが **`site/src/data/new_releases.json`・`site/src/data/catalog/` の中のファイル・`site/src/data/doujin.json`・`site/src/data/game.json` だけ**であることを確認する。他のファイルが変わっていたらコミットしない
7. コミット → ブランチをpush → PRを作る（`gh api repos/juice0402/fanza-ranking/pulls`。CLAUDE.md の守ること1・2）
   - コミットメッセージ: `コメントの仕上げ（Claude）: N件 [CI Skip]`（ブランチのコミットメッセージの最後に `[CI Skip]` を付ける。運営者が Cloudflare の自動ビルドを止めるまで、Cloudflare 側のプレビューを動かさないための保険。データだけのPRなので、CI もプレビューを作らない。待つのは CI（check）だけ）
   - PRのタイトル: `コメントの仕上げ（Claude）: N件`（`[CI Skip]` を入れない）
8. CIが終わるまで待つ（`gh api repos/juice0402/fanza-ranking/commits/<ブランチの先頭>/check-runs` で `conclusion` を見る。数分）
   - **緑ならMerge**（`gh api -X PUT repos/juice0402/fanza-ranking/pulls/<番号>/merge -f merge_method=merge -f sha=<先頭> -f commit_title="Merge #<番号>: コメントの仕上げ（Claude）: N件" -f commit_message=""`。Merge すると、公開（`deploy.yml`）が自動で動く）
   - 赤・時間切れ・衝突（Mergeできない）のときは**Mergeしない**。PRを開いたまま、理由を報告して終了する。衝突のときは、ブランチを捨てて手順1からやり直してよい（1回だけ）
9. Merge したら、公開（Deploy）が終わるのを待つ（ビルド・点検・アップロードで10〜15分）: `gh api "repos/juice0402/fanza-ranking/actions/workflows/deploy.yml/runs?branch=main&per_page=3" --jq '.workflow_runs[] | .status + " " + (.conclusion // "") + " " + .head_sha[0:7]'`
   - Merge のコミットの実行が `completed success` なら公開済み。`cancelled` は、あとの公開（いちばん新しい実行）に含まれたということなので、そちらを見る
   - `failure` なら、理由を注釈で見て報告する（`gh api repos/juice0402/fanza-ranking/check-runs/<id>/annotations`。サイトは前の公開のまま）。30分たっても終わらなければ「公開を確認できず」と報告する
10. 最後に報告する: 何件書いたか（下書きの仕上げ・定型文・予約の言い方の書き直し・過去作品・同人・ゲーム、それぞれ）／PR番号／CIの結果／Mergeしたか／公開（Deploy）の結果／残りの件数（毎日の更新の作品・過去作品・同人・ゲーム）

Mergeしてよいのは、**このコメント更新のPR（データファイルだけを変えるもの）で、CIが緑のとき**だけです（運営者の許可済み）。

## 書き方

目標は、**読んだ人が「どんな作品か」をはっきりつかめる、読みごたえのある紹介文**です。運営者の希望（2026-10-04）で、**書ける範囲で、できるだけ的確に作品の内容（設定・関係・展開の雰囲気）を伝える**。見に来る人は、作品がフィクション・演技であると分かったうえで来ている（作品の冒頭にもフィクションと書いてある）ので、セクハラ・寝取り・催眠・痴漢・拘束のような設定も、設定としてそのまま伝えてよい。
下書き（`draft`）は、材料として読むだけにします。言い回しをなぞらず、**事実を確かめ直して、一から書き上げる**つもりで書きます（下書きと同じ文は `apply` が断ります）。

### 形（2〜3文・100〜160文字）

- 100〜160文字・2〜3文の「です・ます」調（`min_len`〜200文字まで受け付ける。短いと `apply` が断る。`min_len` は、ふつう100、書ける事実が少ない作品（予約で収録時間もジャンルもまだ無い・タイトルを見せない）は80。事実が少ないのに100文字へ水増ししないため）。上品で、落ち着いた、読んで楽しいトーン
- **1文目: 作品の内容を、できるだけ的確に伝える**（`title` があるときだけ）。タイトルを手がかりに、**舞台・登場人物の関係・設定・展開の雰囲気**を、自分の言葉で具体的に書く。ぼかしすぎて何の作品か分からない文にしない
  - 例: 「社内で噂の美人OLに、仕事の相談からドライブデートへ誘われ、そのままホテルへ向かう流れを描いた作品です」「残業で人の少ないオフィスに残った新人OLと中年の部長を描く、セクハラもののオフィスドラマです」「年金暮らしの男の家に住みついたサキュバスを、催眠で思いのままにしようとするファンタジー仕立てのドラマです」「彼女がいるのに、高級ラウンジのキャストに店内で誘惑される、NTR風の主観VRです」
  - **`fiction_theme: true`**（同意の無い場面・薬・嫌がらせ・制裁などを含む設定）の作品も、その設定を伝えてよい。「セクハラもの」「寝取られもの」「催眠」「痴漢もの」「監禁風」「ハード系」「強引な展開」のような、設定やジャンルを表す落ち着いた言葉で書き、暴力そのものを細かく書いたり、あおったりしない
  - **行為・体の部位を直接さす言葉は書かない**（タイトルにあっても使わない。`apply` が断る一覧は下）。「濃厚な絡み」「開発もの」「後ろの開発」「言葉責め」のような、伝わる言いかえを使う
  - **タイトルの言葉を、そのまま長く写さない**（10文字以上つづけて同じだと `apply` が断る）。自分の言葉で、短く、ぼかして言いかえる
  - **`title_hidden: true` の作品は、内容に触れない**。タイトルを見せないのは、**未成年を連想させる**作品だけ（学生・生徒・制服・学園・J●・女子○生・ロリ・幼 など）。これは、フィクションであっても、Claude が未成年の設定を性的な作品として紹介する文は書けないため。内容を推測して書かない。大人どうしの言葉の一部（幼なじみ・姉妹・母娘・男の娘・女の子・処女）では隠さない
  - **`content_off: true`（未成年を連想させるタイトル）の作品は、場面・関係のジャンルにも触れない**。出演者・メーカー・形式（VR・4K・独占配信など）・日付・収録時間だけで、落ち着いた事実の紹介にする（`list` もその作品には形式のジャンルしか出さず、`apply` も場面のジャンルが入っていれば断る）
- **2文目: 出演者・メーカー・形式**など、作品の事実を自然な文で
- **3文目（あれば）: 結び**。作品ごとに変える（収録時間や発売日を添えて言い切る／同じ出演者・メーカーのほかの作品にふれる／形式（VR・8K）の楽しみ方／くわしくはFANZAのページで など）
  - **サンプル動画・サンプル画像に触れるのは、まとめて書く分の3本に1本まで**（2026-10-04 の試運転で、40本ほぼすべてが「サンプル動画と12枚の画像で雰囲気を確かめられます」で終わり、型どおりの文章になった。6本以上まとめて書くとき、「サンプル」「雰囲気を確かめ」「公開されています」などが3本に1本より多いと `apply` が断る）

### 使ってよい情報（これ以外は書かない）

- タイトル（`title`。あるときだけ。上の決まりで、内容の手がかりとしてだけ使う）
- 出演者（`actress`）・メーカー（`maker`。`null` なら触れない）
- 形式（`tags`。VR / 8K など）
- 発売日（`date`）と、発売済みか予約か（`status`）
- 収録時間（`duration_min`。分。`null` なら触れない）。「約150分」のように事実だけ。「長い」「短い」などの評価はしない
- シリーズ・レーベル（`series`・`label`。あるときだけ。2026-10-07 から。レーベルはメーカーと違う名前のときだけ出る）。「○○シリーズの一作」「××レーベルから」のように書いてよい（毎回は書かない。名前は、タイトルを写したことには数えない）
- ジャンル（`genres`。決めた一覧にあるものだけが出る。舞台・関係・形式を表す、おだやかなもの）。「OL・お姉さんのジャンルに入る一本」「ドラマ仕立ての作品」のように書く
- サンプル動画の有無（`sample_movie`）・サンプル画像の枚数（`sample_images`）。**ページで見られるもの**として書いてよいが、**毎回は書かない**（3本に1本まで。上の「結び」）。0枚・無しのときは触れない

### 読みやすさ

- 事実を並べただけの「〇〇さん出演、△△の新作、発売は○日、収録は約○分です。」のような**箇条書きの文にしない**。1文ごとに役目（内容・事実・ページの案内）を分ける
- 文のリズムを整える。「〜の、〜の、〜の」と「の」が3回以上続かないようにする。同じ語尾（「です。」「です。」）を続けない
- 出演者名・メーカー名は、自然な形で1回ずつ入れる（検索で探す人の言葉になるため。同じ出演者名を2回以上入れると `apply` が断る）。4人以上の共演は「〇〇さんほか3人の共演」のようにまとめる
- 予約の作品は「11月1日発売」のように**日付で**書く（「発売されます」「出ます」「控えています」は、発売日をすぎると古くなるので `apply` が断る）。発売済みの作品は「10月4日に発売された」「発売中」と書いてよい

### 書き分け（似た文章の量産に見えないように）

- 書き出しを作品ごとに変える（舞台・関係／出演者名／メーカー名／形式／ジャンル／サンプル動画 など、どこから入るか）
- 結びを変える（言い切る／ページで見られるものを案内する／発売日を添える／くわしくはFANZAのページで）
- 「気になる方は」「チェック」「ぜひ」「いまのうちに」「お早めに」「お見逃しなく」「おすすめ」は、まとめて書くときに使いすぎない（多すぎると `apply` が警告を出す）
- 同じ文を使い回さない（使い回すと `apply` が断る）
- **文字数が足りないとき、同じことを言い直して水増ししない**。事実（ジャンル・形式・発売日・収録時間・同じ日やメーカーのほかの掲載作品など）を1つ足す。1つのコメントの中に、10文字以上同じところがある文が2つあると `apply` が断る（2回目の試運転で「長めの作品を探す方に向いています。長めの作品を探す方にも向いています。」のような文があったため）
- 「出演者の名前から、ほかの作品へもたどれます」「〜な方に向いています」のような決まり文句も、3本に1本まで（多いと `apply` が断る）

### 書かないこと（`apply` が断るものを含む）

- タイトルから分からない中身を**作らない**（タイトルに書かれた設定・関係・展開は伝えてよいが、書かれていない筋書き・出来の良し悪し・「最高の」「見どころ満載」のような評価は書かない）
- 出演者の経歴・容姿・年齢・人気・知名度など、確かめられないことを書かない（「おなじみの」「大人気の」など）
- **確かめられない評価・大げさな言い方**（「待望」「話題」「熱い視線」「期待が高まる」「注目の」「人気の」「ファンの」「必見」「極上」「圧倒的」「豪華な」など）
- **日がたつと古くなる言い方**（「今日」「明日」「今週」など）と、**発売日をすぎると古くなる言い方**（「予約受付中」「発売予定」「発売前」「まもなく」「〜を前に」）。予約の作品も日付だけで書く
- **過激・直接的な表現、性的な行為・体の部位の言葉**（`EXPLICIT_WORDS`: 「中出」「セックス」「フェラ」「アナル」「エロ」「伏せ字の●」など。性的暴行・連れ去り・拷問・人をモノ扱いする言葉（「レイプ」「凌辱」「拉致」「便器」「奴隷」など）も書けない。「寝取」「NTR」「催眠」「痴漢」「セクハラ」「拘束」「調教」「監禁」「媚薬」は、設定を表す言葉として書ける）。**未成年を連想させる言葉**（`MINOR_WORDS`: 「制服」「学生」「妹」「娘」「少女」「童顔」など。**学校・子どもの生活を連想させる場面**の「学園」「職業体験」「家庭教師」「放課後」「部活」なども。大人の女性を「女の子」とも書かない（「女性」と書く）。こうした言葉があるタイトルは、はじめから見せない）
- 挨拶・前置き・絵文字・飾りの記号・マークダウン・URL・改行

### 書き方の例（名前・設定は仮のもの）

- タイトル「会社で噂の先輩OLに仕事の相談をして、ドライブデートに誘われた…」・出演〇〇さん・メーカー△△・約246分・サンプル動画あり・画像12枚
  → 「職場の先輩とのドライブから始まる、オフィスものの一本です。〇〇さんが先輩OL役で出演する△△の作品で、収録は約246分。10月4日に発売され、出演者の名前から、ほかの出演作もたどれます。」
- タイトル「高級ラウンジで出会った…」・VR・8K・ジャンル（お姉さん・スレンダー）
  → 「高級ラウンジを舞台に、大人の駆け引きを描くVR作品です。〇〇さんがお姉さん役を演じる、△△の8K収録の一本。11月1日の発売で、ページには出演者のほかの作品へのリンクもあります。」
- `title_hidden: true`・出演〇〇さんほか3人・メーカー△△・約180分
  → 「〇〇さんほか3人が共演する、△△の約180分の作品です。出演者の一覧から、それぞれの出演作もたどれます。発売は10月4日で、くわしい内容はFANZAの作品ページで確かめられます。」

### 同人・ゲームの書き方（2026-10-09 から）

形・点検・書かないことは、動画と同じです（2〜3文・100〜160文字・行為や体の言葉は書かない・確かめられない評価は書かない・タイトルを10文字以上写さない）。ちがうのは、使える事実です。

- **1文目: 作品の内容**を、タイトルを手がかりに、舞台・登場人物の関係・設定・展開の雰囲気で伝える（動画と同じ。`fiction_theme: true` の作品は、設定として落ち着いた言葉で）
- **2文目: 作り手**。同人は「サークル○○の同人作品」、ゲームは「ブランド○○のPCゲーム」「原画・シナリオなどは○○」（`authors` は、役目が分からないので「作家として○○の名前があります」くらいにする）。シリーズがあれば「○○シリーズの一作」
- **3文目（あれば）: ジャンル・発売日・サンプル画像の枚数**などで結ぶ（ゲームは「ファンタジーの世界を舞台にした恋愛アドベンチャー」のように、ジャンルから遊び方の形を伝えてよい）
- **書かないこと**: 価格・割引・セール・クーポン（毎日変わるので、ページの価格の欄にまかせる）・順位・レビューの点数・「人気」「売れている」。ページ数・プレイ時間・対応OSは、`list` に出ないので書かない
- 同人・ゲームのデータには、未成年を連想させる作品は入っていない（集めるときに外している）。それでも `title_hidden` が付いた作品があれば、動画と同じく内容に触れない

- 例: タイトル「森の奥の魔法使いと、ふたりきりの冬」・サークル△△・ジャンル（ファンタジー・純愛）
  → 「森の奥で魔法使いとふたりきりで過ごす、冬の日々を描いた物語です。サークル△△による同人作品で、ファンタジーの世界を舞台にした純愛ものとしてまとめられています。9月30日に発売されました。」

## うまくいかないとき

- `apply` が断ったとき: 表示された理由（文字数・使えない言葉・下書きと同じ・同じ文の使い回し・同じ内容の言い直し・決まり文句の使いすぎ など）を直して、もう一度実行する
- 仕上げ済みのコメントに問題が見つかったとき（運営者に頼まれたとき・見直しで見つけたとき）だけ、`apply ファイル.json --rewrite` で書き直せる（点検は同じ）。**毎日の予約タスクでは使わない**
- 運営者に頼まれて、会話の中で Claude が1本ずつ書くときだけ、`--no-daily-limit` で1日40件の上限を数えずに書ける（2026-10-04、全作品の点検で使った）。**毎日の予約タスクでは使わない**
- CIが赤いとき: Mergeせず、PRを開いたまま報告する（運営者がClaudeに相談する）
- リポジトリに入れない／PRを作れないとき: 無理に回り道をせず、できなかった理由を報告して終了する（データは壊れていないので、次の日にもう一度やればよい）
- 1日抜けても大丈夫: 次の日の実行が、残りもまとめて書き上げる（下書きのあいだも、サイトには Gemini の文が出ている）
