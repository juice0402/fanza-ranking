# 設計メモ・今後の予定

## デザインの考え方「新作棚」

レンタルビデオ店の新作コーナーのイメージ。

- トップは**発売日ごとの棚**。日付の見出し（タブ）の下に、その日発売の作品が並ぶ
- 「新作」（発売から6日以内）「予約」のシールを付ける。表紙の画像を広く見せるため、メーカー名の縦帯は付けない（メーカーは作品ページ・出演者/メーカーのページで見られる）
- 作品ページのサンプル画像は、タップで画面いっぱいに拡大（前後ボタン・左右スワイプ・Escで閉じる。`site/public/lightbox.js`。JavaScriptが使えない環境では、画像が別タブで開く）
- 作品カードの題名は、2行でも3行でも**3行ぶんの高さを確保**する（`.item-title` の `min-height`）。横に並んだカードで、出演者・コメント・ボタンの位置がそろう（題名は3行を超えると省略）
- ジャケットはDMMの `pl.jpg`（横長）の**右半分**を切り抜いて縦長の表紙として使う
- 「発売中の新作」と「予約受付中」は別セクション。発売中が0件のときは案内文を出す
- スマホ（特に小さい画面）を主役にして作る。ボタンは44px以上、文字の折り返しは `.phrase` と `text-wrap: balance` で整える
- 広告の表記: ヘッダーのブランド名の横に小さな「広告」ラベル（最初に見える画面に必ず出す）、くわしい文はフッター。作品ページのボタンの下の「広告｜リンク先は…」の行は、運営者の希望でやめた（文字が多くなるため）。以前の「ページ最上部の細いバー」はやめた（見た目を軽くするため）。JavaScriptが無効のときだけ、18歳未満は使えないという注意書き（`noscript-note`）が上に出る。`verify_dist.py` が、ラベルの位置（ヘッダーの中・メニューより前）・隠れていないこと・11px以上・フッターの文を全ページで検査する。フッターだけにしないのは、ASP（楽天アフィリエイトなど）の案内が「ファーストビューに表示」「下部・フッターだけは不適切」としているため（ステマ規制）

見た目の設定（色・余白など）は `site/src/styles/site.css` の先頭にまとめてある。

## 分かっていること・注意点

### FANZA(DMM) アフィリエイトAPI
- `sort=date` は**発売日が遠い予約作品から**返ってくる。そのままだと一覧が予約だらけになるため、「発売済み」と「予約」を日付の範囲指定で**別々に取得**している
- `gte_date` / `lte_date` の指定は、公式ドキュメントを開けない環境で作ったため、**本番で動いた実績がまだない**。初回の手動実行で、ログの `🔎 取得: 発売済みN件 / 予約M件` を確認すること。APIがエラーを返すと `exit 1` で止まる（データは壊れない）
- **出演者が空の作品**: FANZAは予約作品に出演者を**あとから載せる**ことがある（2026-10-03 時点の空の5件は、どれも予約）。毎日の更新が、空の出演者を補う。①今回の取得（発売済み100件・予約4件）にもう一度出てきた作品は、その応答で補う（`refresh_from_fetched`。追加の呼び出しなし）。②出てこなかった作品は、**品番（`cid=`）を指定して取り直す**（`refetch_by_cid`。1回 `REFRESH_PER_RUN`=20 件まで、発売日の `REFRESH_WINDOW_DAYS`=30 日後まで、出演者が空の作品が先）。すでに出演者がある作品は書き換えない。補ったら `updated` を進める。続けて3回失敗したらその回はやめる（データは壊さず保存する）
  - Web検索で出演者を補う案も試したが、品番・タイトルで検索しても無関係なページばかりで、DMMのページは robots.txt で読めなかった。「2つ以上のサイトで一致したときだけ入れる」を守ると、ほぼ空欄のままになるため、いまは作っていない（出演者を推測で入れない）
  - **素人もの・名前を伏せた作品**: 運営者の案（ファンサイトのWikiなどで、実は出演している女優名を調べて入れる）は、**採用しない**と決めた。名前を伏せるのは作り手の意図であること、別人に当てはめる誤りや、特定してはいけない人を特定してしまうおそれがあること、確かめる手段がClaude側に無いことが理由。FANZAが後から出演者を載せたときだけ、上の仕組みで自動で入る
  - FANZAのユーザーコメント: 公式APIに無く、DMMのページは robots.txt で自動取得が禁止されているため、使えない
- **サンプル動画**（ItemListの `sampleMovieURL`）: `size_476_306` などのページURL（FANZAの動画プレイヤーのページ）と `pc_flag` / `sp_flag`。**パソコン・スマホの両方が 1 のときだけ**使う（`pick_sample_movie`）。保存は `sample_movie`（476x306のURLだけ。DMMのhttpsだけ通す）と `movie_tries`（発売後なのに動画が無い作品を取り直した回数。3回であきらめる）。動画がいつ載るか（予約のうちから載るか、発売後か）は、まだ確かめていない。取り直しは**発売済みの作品だけ**を対象にしている
- **出演者のプロフィール**（`ActressSearch`。本物のAPIで形を確かめた）: 体型は**文字列**（"86"）で、新人は多くが null。画像のURLは http なので https に直す。`listURL.digital` は「その出演者のFANZAでの全作品」のアフィリエイトURL。保存するのは 名前・読み・顔写真(small/large)・バスト・カップ・ウエスト・ヒップ・身長・生年月日・全作品リンク・取得日だけ（血液型・趣味・出身地は保存しない）。1回30人まで（新しく見つけた人 → 名前だけ分かっている人（キーワード検索で完全一致が**ちょうど1人**のときだけ採用。同名・見つからないときは `unmatched` に覚えて、30日後まで探さない）→ 30日たった人の取り直し）
  - **取り違えを防ぐ決まり**: 名前での検索は100件まで頼み、応答の `total_count` が一覧より多い（途中で切れている）ときは、完全一致が1人でも採用しない。id で取り直した応答が中身の無い行（顔写真・体型・生年月日・リンクのどれも無い）のときは、保存済みの内容を消さず、取得日だけ進める。取り直した作品で分かった出演者の id も、プロフィール取得に使う。`actresses.json` が壊れて読めないときは、出演者プロフィールの更新だけをやめて（ファイルは上書きしない・警告を出す）、新しい作品の追加やコメントは続ける
  - **取り直しの枠**: 1回20件のうち、出演者が空の作品には発売日が今日に近いものから、サンプル動画には新しいものから使う。どちらかが多くても、もう一方に最低10件分は残す（出演者を伏せたままの作品が増えても、動画の取り直しが後回しにならないため）
  - **形式タグ**: 英数字6文字までのもの（VR・8K など）だけ。タイトルの【】の中の日本語は、タイトルの一部なので、AIへの依頼にも定型文にも使わない（取得時も、保存済みデータの読み込み時も絞る）
- **売れ筋ランキング**: `sort=rank`（人気順）の上位6本を `ranking.json` に保存する（画面に出すのは先頭3本。残りは、VR作品を隠したときの差し替え用）。各行に `vr`（VR作品か。題名の【VR】・形式タグ・ジャンルから、取得のときに判定。`is_vr_item`）を持たせる。**FANZAのサイトにある「デイリーランキング」と同じ順位とは限らない**（APIの `rank` は「人気順」）。画面では「売れ筋」と書き、「デイリーランキング」とは書かない。取得に失敗したら前回のものを残す
- サンプル動画のページは、アメリカのGitHub Actionsからは国の制限（地域ブロック）で見られない。**動画が実際にiPadで再生できるか**は、PRのプレビューで運営者が確かめる（作品ページは、動画のURLがあるときだけ動画の枠を出し、見られないときのためにFANZAへのリンクを添える）
- 作品の重複は `cid`（content_id）で判定する。保存データに読めない作品（`cid` かタイトルが無い）があると、作品が消えないよう実行を止める

### Gemini（コメント生成）
- アダルト作品はセーフティフィルターで**ブロックされやすい**。作品タイトルは渡さず、出演者・メーカー・形式タグ（VR / 8K など）だけを渡す
- **コメントの書き分け（2026-10-04）**: 以前は切り口が3つだけで、どのコメントも「出演者＋メーカー＋日付＋『気になる方はチェック』」の同じ型になりやすかった（94本の調査: 結びに「チェック」が19本・「気になる方は」が15本。文章そのものは別物で、2つの文の似かたの平均は0.09だが、読んだ感じが似る）。そこで `build_prompt` に、**切り口6種類×書き出し4種類×結び4種類**を作品ごとに決めて渡す（`stable_number` で決まるので、同じ作品・同じ回数なら同じ。再挑戦では変わる）。使いすぎる結び（`AVOID_PHRASES`）は使わないよう頼む。収録時間（事実）も渡す。「前向きなトーン」という頼み方と「発売されるタイミングの注目度」という切り口は、「待望」「熱い視線」のような確かめられない評価を生んでいたのでやめた
  - **確かめられない評価（`HYPE_WORDS`）・過激な言葉・未成年を連想させる言葉が答えに入っていたら採用しない**: 定型文にして、再挑戦の回数を1増やす（上限3回。それでも続けば Claude が書き直す）。Gemini の回数は増えない。一覧は `scripts/claude_comments.py` と同じ（`tests/test_script.py` が同じかを調べる）
  - **予約中の作品には、「予約受付中」「発売予定」など発売日をすぎると古くなる言い方を使わせず、「○月○日発売」と日付で書かせる**。すでに保存済みで古くなったもの（発売日をすぎたのに予約の言い方が残るコメント）は、Claude の毎日の予約タスクが書き直す（`claude_comments.py list` の対象）
  - 古い方式（タイトルを渡していた時期）で作ったコメントは、作品の内容の断定や強い言葉が入っていたので、2026-10-04 に書き直した（PR #36。28件）
- ブロック・失敗した作品は、出演者やメーカー入りの**代替文**（`comment_kind: template`）にして先に進み、次回以降に別の切り口で再挑戦（1回の実行で最大4件、1作品あたり最大3回）
- **無料枠は「1日20回ほど」**（`gemini-3.6-flash`。2026年9月時点の他の利用者の報告と、実際のActionsログによる。Google公式では数字を確認できていない）。上限は**プロジェクト単位**で、太平洋時間の0時（日本時間の午後4時ごろ。冬時間は午後5時）にリセットされる。上限を超えると HTTP 429 になる
  - 2026-10-03 の実行で、最初の3件だけAIコメントが付き、あとは 429/503 になった（ブロックではない）
  - そのため1回の実行は **新規12＋予約4＋再挑戦4＝20回** に収めている（`NEW_ITEMS_PER_RUN` / `UPCOMING_ITEMS` / `RETRY_PER_RUN` / `GEMINI_MAX_CALLS`）
  - 1日の上限に当たったら待たずにお休みする（待っても治らない）。1分あたりの上限なら、Geminiが教える待ち時間（`retryDelay`）だけ待つ
  - **手動実行は1日1回まで**。枠は日本時間の午後4時に新しい1日になり、毎日0:05の自動実行はその日の終わりに近い時間帯に動く。手動で動かすと、そのぶん次の0:05の自動実行で使える枠が減る（足りない分はClaudeが書き足す）
  - もっと多く欲しいときは**有料枠**（Google AI Studio で請求先を登録）にして、上の4つの数字を増やす
- 連続で3回失敗したら、その回はAI呼び出しをやめる。呼び出しの間隔は既定5秒
- 実行結果の要約（取得件数・AIの成功数・お休みした理由）は、ActionsのRunのページの上に出る。エラーの理由は `⏳`/`⛔` の行にも出る
- 画面には、フッターに「ひとことコメントは、…作品情報をもとに自動で作成しており、内容の正確さは保証できません」と注記している（運営者の希望で「AI」という言葉は出さない。注記そのものは残す。2026-10-03）。代替文は文章のコメントとして扱わない（`isAi` は `comment_kind` が `ai` か `claude` のときだけ）
- Geminiが書けず代替文のまま残った作品は、**Claudeの予約タスク**（毎日 0:20 JST）があとから書き直す。Gemini と違って回数の上限を気にしなくてよい（運営者のClaudeプランの利用枠で動き、APIキーは不要）。道具は `scripts/claude_comments.py`、手順と書き方は [claude-comments.md](claude-comments.md)。**2026-10-04 から、Gemini の文は「下書き」（`comment_kind: ai`）で、Claude が毎日読み直して書き上げたものを `comment_kind: claude` として保存する**（運営者の希望「Geminiの文を、Claudeが読み直して素晴らしい文章にしてから公開」）。下書きが出ているのは、0:05 の更新から 0:20 の予約タスクのPRがMergeされるまでの十数分だけ。それ以前の94件（Claude が書き直した28件を含む）も、すべて下書き扱いで、数日かけて書き上げ直す（1回40件まで。定型文・予約の言い方が残るものを先に）。Claude に渡すのは、出演者・メーカー・形式・発売日・収録時間・ジャンル（決めた一覧だけ）・サンプル動画の有無・サンプル画像の枚数と、下書き。タイトルは渡さない

### データ
- `site/src/data/new_releases.json` は毎日増える（1日あたり最大 約16件。無料枠に合わせた数）。作品ページが1件ごとに作られるので、**数千件を超えてビルドが遅くなったら**、年月ごとにデータを分けるなどの対策を考える
- 日付はすべて日本時間で扱う（ビルドするサーバーの時刻設定に左右されない。`jstToday`）
- 作品ごとの `updated` は、その作品のデータ（コメント）を最後に変えた日（日本時間 YYYY-MM-DD）。新しく追加した日と、コメントが変わった日（Geminiの再挑戦・Claudeの書き直し）に進める。sitemap の `<lastmod>` に使う（トップ・一覧は、`updated` と「発売日を迎えた日」のうち一番新しい日。`listLastmod`）。分からない日付は作り出さず、`lastmod` を付けない
- **「発売中」と「予約」の表示は、ビルドした時点の日付で決まる**（サイトは静的に作るため）。毎日の更新を日付が変わった直後（0:05）にしているので、その日に発売される作品は朝から「発売中」で表示される。更新が失敗した日は、前日の表示のまま（発売日を迎えた作品も「予約」）になる

## 出演者の顔・検索、サンプル動画、売れ筋（2026-10-03 追加）

データは「分かっていること・注意点」の各項目（出演者プロフィール・サンプル動画・売れ筋ランキング）。ここは画面側の考え方。

- **出演者の顔**: 名前の左に丸い顔写真（FANZA公式の出演者データ）。写真が無い・読み込めないときは、名前の頭文字が出る（写真を文字の上に重ねる作りで、`onerror` で写真を消せば文字が見える）。作品ページ・一覧・検索結果・出演者ページの見出しで使う。幅の狭い画面（480px以下）では、見出しの顔を小さくして、名前の場所を空ける
  - 本物のデータでは、プロフィールを調べた150人のうち、顔写真があるのは約88%、FANZAの全作品リンクは100%、スリーサイズは約32%、身長は約30%、年齢は約20%（2026-10-03）。新人ほど数字が空
- **出演者検索（`/actress/`）**: 名前（ひらがな・カタカナでも）・年齢・身長・バスト・ウエスト・ヒップ・カップで絞り込む。JavaScript が使えないとき・索引を読めないときは、最初から載っている一覧（作品2本以上の出演者）がそのまま使える
  - 検索のもとは `/data/actresses-index.json`（ビルドごとに作る。下の「女優検索を、FANZA公式の名簿で」で形を変えた）。**生年月日は入れない**
  - 作品が2本以上ある人は専用ページ（`s` あり）へ、それ以外の人は「FANZAで全作品を見る」へリンクする
  - **数字で絞り込むと、数字が載っていない人は結果に出ない**（載っていない値を「条件に合う」とは言えないため）。画面にも注意書きと、調べ済みの人数・数字が載っている人数を出している
  - 年齢は、生年月日から**ビルドの日に計算**（毎日更新されるので、ずれは1日以内）。18〜80歳の範囲外は捨てる
- **サンプル動画（作品ページ）**: 動画があれば、いまのパッケージ画像の場所を動画にして、パッケージ写真は「サンプル画像」の下に、「パッケージ写真」という別の欄で大きく出す（最大800px幅。サンプル画像の並びに混ぜると、パッケージ写真も入って9枚になり、並びが崩れやすかったため。2026-10-03に変更）。拡大表示は、サンプル画像→パッケージ写真の順に送る（ラベルは「サンプル画像 N」「パッケージ画像」）。動画が取れなかった作品は、これまでどおりパッケージ画像が上（別の欄は作らない）
  - FANZAの再生ページ（476x306）を `iframe` で埋め込む。枠の幅に合わせて、`transform: scale` で拡大・縮小する（`movie.js`。JavaScript が使えないときは等倍）
  - `iframe` に `sandbox` は付けていない（付けると、FANZAのプレイヤーが動かなくなるおそれがあるため。埋め込むのはFANZA(DMM)のhttpsのURLだけで、`safeHttpsUrl` が通したものだけ）。**動画がiPadで実際に再生できるかは、まだ確かめていない**（アメリカのGitHub Actionsからは、国の制限で再生ページを開けない）。見られないときのために、「FANZAで見る」のリンクを添えている

## SEO（検索から来てもらうための作り）

- 検索エンジンに伝える情報: `<title>`・説明文・canonical・OGP（全ページ）、sitemap（`<lastmod>` つき）、robots.txt、構造化データ（JSON-LD。トップは `WebSite`、それ以外は `BreadcrumbList`。画面のパンくずと同じ内容）
- **出演者ページ（`/actress/…`）・メーカーページ（`/maker/…`）**: 掲載が2本以上の人・メーカーだけ作る（`ENTITY_MIN_ITEMS`。1本だけだと内容が薄いため）。作品ページ・トップ・フッターからリンクして、内部リンクを増やす
  - URLは名前のハッシュ（10文字の英数字）。日本語や `/` を含む名前（例: `〇〇/妄想族`）をURLに入れる危険を避けるため。名前は画面の見出し・タイトルに出る
  - 紹介文は作品データ（本数・発売日・メーカー・形式）だけから作る。出演者の経歴や評価は書かない
- **週のまとめ記事（`/weekly/…`）**: 毎週月曜に Claude が、前の週（月〜日）に発売された作品のまとめを1本書く（手順は `docs/claude-roundups.md`）。「FANZA 新作 ○月第○週」のような検索に合う、作品ページとは別の読みもの
  - 記事の文章（導入文・注目の作品のひとこと）だけを `roundups.json` に保存。本数・日別・メーカー別・出演者別・形式別の表は、ビルド時に作品データから数える（文章の数字が間違っても、表は正しい）。作品が10本に満たない週は書かない
  - 文章に使えるのは作品データの事実だけ（出演者・メーカー・形式・日付・収録時間）。タイトルは見せない（コメントと同じ理由）。文章中の数字は、一覧にある数字しか使えない（`apply` が検査）
  - 1本も無いあいだは、一覧ページ（`/weekly/`）を noindex にして sitemap にも入れず、トップ・フッターからのリンクも出さない（空のページを検索に出さないため）。記事ができると、自動で sitemap・フッター・トップに現れる
  - 構造化データは `Article`（著者・発行元はサイト自身。人の名前は入れない）と `BreadcrumbList`
- **作品ページの「この作品のデータ」欄と品番（2026-10-04 追加）**: 作品ページが「FANZAの情報の写し＋短いコメント」だけだと、Googleの言う「付加価値の少ないアフィリエイトページ」に見られやすいため、ビルド時に掲載データを数えた事実を足した（`site/src/lib/facts.js`。AIは使わない）
  - 行: 同じ発売日の本数（同じメーカーの本数も）、メーカーの掲載本数と発売日の幅、出演者ごとの掲載本数（3人まで）、収録時間の順位（収録時間が分かる作品が10本以上のとき）、VR作品の本数。それぞれ、月・メーカー・出演者・VRのページへリンク（ページがあるときだけ）
  - 書くのは数えた事実だけ。「人気」「おすすめ」のような評価の言葉は入れない（テストで検査）
  - **品番**（例: `DLDSS-556`）を、作品ページのタイトル（先頭）・説明文・作品情報の表に出す。「品番で検索する人」が多いため。保存データに品番は無いので、作品ID（`cid`）から `productCode` で作る。**形がはっきりしているものだけ**（英字2〜8文字＋番号3〜5桁。最後に英字が付くもの・数字が混ざる記号などは作らない）。まれに、本当の品番と違う形になる可能性がある（例: 記号が数字で始まるレーベル）。FANZAのAPIの `maker_product` を保存するようにすれば正確になる（今後）
  - タイトルに名前が入っている出演者は、`<title>` のかっこの中にくり返さない
- **月ごとのページ（`/month/YYYY-MM/`、2026-10-04 追加）**: 「FANZA 11月 新作」のような検索向け。作品が5本以上ある月だけ（`MONTH_MIN_ITEMS`）。月の中は発売日順で、日ごとの見出しに `#day-YYYY-MM-DD` の目印がある（作品ページの「同じ発売日」からその位置へ飛べる）。前の月・次の月へのリンク。部品は `site/src/lib/collections.js`
- **一覧の出演者は3名まで**（2026-10-05。運営者から「オムニバスのような、沢山出演者がいる作品が枠を圧迫して、全体が見づらい」）: カード・作品検索・お気に入り・週のまとめの一覧では、先頭の3名と「ほか○名」（`castLine`・`CAST_LIMIT`）。トップのTOP3は2名。作品ページは、これまでどおり6名以上なら4名＋「ほか○名を見る」でたたむ。あわせて、Chromium で1行の出演者の行が `<wbr>` のところで2行になっていたのを、CSS で `<wbr>` を消して直した
- **拡大表示のボタン**（2026-10-05。運営者から「サンプル画像やパッケージ写真に矢印が被って、内容が見えない。下のほうがいい」）: 前・次のボタンと枚数を、画像の下の帯に並べた（親指でも押しやすい）。閉じるは右上（画像の上に、その分のすき間をあけてある）。横のスワイプ・← → キーはそのまま
- **「この作品のデータ」から収録時間の長さくらべを外した**（2026-10-05。運営者「長さで買っている人はいないと思う」）。収録時間そのものは作品ページの基本情報に出す
- **ジャンルのページ（`/tag/<名前のハッシュ>/`、2026-10-04 追加）**: 「巨乳 新作」のような検索向け。作品が3本以上あるジャンルだけ（`TAG_MIN_ITEMS`）。1ページ最大90本（`TAG_PAGE_LIMIT`）。作品ページのジャンルのタグは、そのジャンルのページがあればそこへ、無ければ作品検索（`/search/?tag=`）へリンクする。ほかに、トップ・フッター・`/tag/` 一覧からもリンク
  - **ページを作るジャンルは、`site/src/config.js` の `TAG_PAGE_GENRES` に書いたものだけ**（許可リスト）。理由: (1) ハイビジョン・独占配信・4K・単体作品のような「技術的な区分」は、検索する人がいない・どの作品にも付くので、薄いページが増えるだけ (2) 過激な行為の名前や、制服・学生・「少女」を含むなど未成年を連想させる名前のページは、広告の審査・検索エンジンの扱いで不利になりうるので作らない（作品検索では今までどおり絞り込める）。`tests/verify_dist.py` と `tests/test_seo.mjs` が検査
  - VR作品だけは、ジャンルの名前とは別に、`isVrWork`（タイトルの【VR】・形式タグ・ジャンルの「VR」）で集めた「VR作品」のページを作る
  - 足したいジャンルがあれば、`TAG_PAGE_GENRES` に1行足すだけでよい（3本以上あれば、次のビルドでページができる）
- 作らなかったもの: 一覧ページの `ItemList` 構造化データ（Googleの検索結果での見た目が変わらないため）、noindex による薄いページの間引き（作品ページの中身を増やすほうを先にした。Search Console で「クロール済み - インデックス未登録」が多く出るようなら、次に考える）
- Google Search Console の所有権の確認コードは `site/src/config.js` の `GOOGLE_SITE_VERIFICATION` に入れてあり、全ページの `<head>` に `<meta name="google-site-verification">` として出る（公開されても問題のないコード。消すと Search Console が「所有権を確認できない」になるので、消さない）
- 作らないもの: 作品ごとの `Product` 構造化データ（価格・在庫など確かめられない項目が多く、誤った表示のもとになるため）
- 点検（`tests/verify_dist.py`）: lastmod、構造化データ、h1が1つ、リンク切れなし、sitemapに載るページがnoindexでないこと（noindexのページはsitemapに入れない）、まとめ記事のページ数・`Article`・注目の作品へのリンク、タイトル重複（警告のみ）、品番と「この作品のデータ」欄、月・ジャンルのページの数と sitemap、ジャンルのページに許可リスト外の名前が無いこと

## また来てもらうための機能（お気に入り・発売日カレンダー）

- **お気に入り（☆）**: 作品・出演者・メーカーに ☆ を付けると、「お気に入り」ページ（`/favorites/`）に集まる。出演者・メーカーを登録すると、その人の新作・予約（これから発売＋最近30日）も同じページに出る。トップには「お気に入りの新作・予約が N本あります」の小さなお知らせが出る（予約＋7日以内の発売を数える）
  - **保存先は、見ている端末のブラウザ（localStorage）だけ**。ログインや運営側のデータベースは使わず、何も送らない。そのため別の端末・別のブラウザには引き継がれず、閲覧データを消すと消える（ページにも書いてある）。上限は種類ごとに300件
  - 新作の探し方: ビルドのたびに作る小さな索引（`/data/favorites-index.json`。最近60日前から先の作品だけ。短い名前 `c,t,d,a,m,i`）を、ブラウザが読んで照らし合わせる
  - JavaScript や localStorage が使えない環境では、☆ボタンを出さない（他の機能は変わらない）。「お気に入り」ページ・カレンダー説明ページは見る人ごとの内容・使い方だけなので noindex・sitemap にも入れない
  - 保存データの形（`fanza-fav-v1`）を変えるときは、`site/public/favorites.js` の `parseStore` が古い形も安全に読めるようにする（壊れた・古いデータは捨てて空として読む作り）
- **発売日カレンダー（`.ics`）**: iPad・iPhone・Googleカレンダーで「購読」すると、発売日が自動で入る（毎日の更新に合わせて、カレンダー側が定期的に読み直す）。すべての発売予定（`/calendar/upcoming.ics`）と、出演者・メーカーごと（`/calendar/actress/<slug>.ics`、`/calendar/maker/<slug>.ics`。専用ページがある人・メーカーだけ）がある。入る作品は、発売日が14日前から先のもの（最大200件）
  - **予定の題名に作品タイトルを入れない**（カレンダーを人に見られても困らないように）。「【発売】○○の新作」とし、タイトル・品番・リンクは詳細（説明）に入れる
  - 発売日の朝9時の通知（VALARM）を付けているが、購読カレンダーで通知が鳴るかは、カレンダーアプリの設定しだい（iPadでの動きは未確認）
  - `.ics` の `Content-Type` が `text/calendar` で配信されるか（Cloudflare Pages）は、公開後に確かめる
- 点検（`tests/verify_dist.py`）: お気に入り・カレンダーのページと noindex・sitemap の関係、索引の形、`.ics` の形（CRLF・75バイト折り返し・BEGIN/END の対応・UID の重複なし・題名にタイトルが入っていない）、出演者・メーカーのページと `.ics` が1対1、☆ボタンの有無
