# 設計メモ・今後の予定

## デザインの考え方「新作棚」

レンタルビデオ店の新作コーナーのイメージ。

- トップは**発売日ごとの棚**。日付の見出し（タブ）の下に、その日発売の作品が並ぶ
- メーカー名は縦の背ラベル風に表示。「新作」（発売から6日以内）「予約」のシールを付ける
- ジャケットはDMMの `pl.jpg`（横長）の**右半分**を切り抜いて縦長の表紙として使う
- 「発売中の新作」と「予約受付中」は別セクション。発売中が0件のときは案内文を出す
- スマホ（特に小さい画面）を主役にして作る。ボタンは44px以上、文字の折り返しは `.phrase` と `text-wrap: balance` で整える

見た目の設定（色・余白など）は `site/src/styles/site.css` の先頭にまとめてある。

## 分かっていること・注意点

### FANZA(DMM) アフィリエイトAPI
- `sort=date` は**発売日が遠い予約作品から**返ってくる。そのままだと一覧が予約だらけになるため、「発売済み」と「予約」を日付の範囲指定で**別々に取得**している
- `gte_date` / `lte_date` の指定は、公式ドキュメントを開けない環境で作ったため、**本番で動いた実績がまだない**。初回の手動実行で、ログの `🔎 取得: 発売済みN件 / 予約M件` を確認すること。APIがエラーを返すと `exit 1` で止まる（データは壊れない）
- 作品の重複は `cid`（content_id）で判定する。以前のデータ（`cid` なし）は、URLから `cid` を取り出して移行済み（`cid_from_old_item`）

### Gemini（コメント生成）
- アダルト作品はセーフティフィルターで**ブロックされやすい**。作品タイトルは渡さず、出演者・メーカー・形式タグ（VR / 8K など）だけを渡す
- ブロック・失敗した作品は、出演者やメーカー入りの**代替文**（`comment_kind: template`）にして先に進み、次回以降に別の切り口で再挑戦（1回の実行で最大6件、1作品あたり最大3回）
- 連続で3回失敗したら、その回はAI呼び出しを休む（429対策）。呼び出しの間隔は既定5秒
- 画面には「コメントの一部はAIが自動で作成」と注記している。代替文もAIの文として扱わない（`isAi` は `comment_kind === 'ai'` のときだけ）

### データ
- `site/src/data/new_releases.json` は毎日増える（1日あたり最大 約30件）。作品ページが1件ごとに作られるので、**数千件を超えてビルドが遅くなったら**、年月ごとにデータを分けるなどの対策を考える
- 日付はすべて日本時間で扱う（ビルドするサーバーの時刻設定に左右されない。`jstToday`）

## 今後やりたいこと（優先度の高い順の目安）

1. **初回の本番更新の確認**（運営者）: Actions →「Daily FANZA Update」→ Run workflow。ログの `取得: 発売済みN件 / 予約M件` と、サイトに作品が並ぶことを確認
2. **本物のジャケットでの見た目確認**: 右半分の切り抜きが、実際の画像でも自然か
3. **出演者ページ・メーカーページ**: ページ数・内部リンクが増え、検索から入る入口も増える（SEO）。部品は `relatedItems` などがすでにある
4. **Google Search Console に sitemap を登録**（運営者）: `https://fanza-ranking.pages.dev/sitemap.xml`
5. **独自ドメイン**: `site/src/config.js` の `SITE_URL` を変え、Cloudflare側でドメインを設定
6. **スクリプトの分割**: `get_new_releases.py` が長くなって読みにくくなったら、取得・コメント・保存に分ける（テストが守ってくれる）

## 開発環境の約束

- 変更はブランチ+PR。PRごとに `ci.yml`（テスト+ビルド+全ページの点検）と Cloudflare のプレビューが動く
- `bash scripts/check.sh` がローカルでの合言葉。ビルドまで見るなら `--build`
- 本番データ（`new_releases.json`）はテストに使わない。テストは `tests/fixtures/` の固定データで動く
