# Claude による週のまとめ記事（毎週月曜の予約タスク）

毎週月曜 0:50（日本時間）に、Claude の予約タスクが、**前の週（月曜〜日曜）に発売された作品のうち、当サイトで紹介した作品のまとめ記事**を1本書きます。
公開先は `/weekly/<週の月曜日>/`（例: `/weekly/2026-09-28/`）。検索で「FANZA 新作 10月第1週」のような言葉から来てもらうための、サイトの読みものです。

```
 0:05  GitHub Actions … 新作を取得（月曜の新作もここで入る）
 0:20  Claude の予約タスク（毎日）… 定型文の作品にコメントを書く
 0:50  Claude の予約タスク（毎週月曜）… 前の週のまとめ記事を書く → PR → CIが緑ならMerge → 公開
```

記事の中身は3つです。

- **導入文（lead）**: その週を一言でまとめる文章（80〜300文字）
- **この週の傾向（trend）**: 前の週との比べ・ジャンルの増減・新着の人気順で上位に入った作品から読み取れること（80〜360文字。2026-10-07 から。運営者の希望「ランキングの傾向・考察を加える」）
- **注目の作品（picks）とそのひとこと（note）**: 3〜6本。ひとことは40〜120文字

本数・日別・メーカー別・出演者別・形式別の表は、**サイトが作品データから自動で数えて表示します**（記事のファイルには入れません。Claude が数字を書き間違えても、表は正しいまま）。
傾向の表（本数と前の週との増減・ジャンルの横棒・人気順の上位の作品）は、`apply` が**書いたときの数字を記事と一緒に保存し**（`facts`）、サイトはその数字を表にします（あとで記録が変わっても、文と表が食い違わないように）。
週の作品が10本に満たない週は、記事を作りません（内容が薄くなるため）。

予約タスクの名前は「毎週のまとめ記事（Claude）」です（自動承認の設定）。止める・時間を変える・手順を変えるときは、Claudeに頼んでください（手順そのものは、予約タスクが毎回このファイルを読むので、このファイルを直せば反映されます）。

## 手順

1. リポジトリ `juice0402/fanza-ranking` を使える状態にする（無ければ add_repo → clone）。`main` を最新にして、作業用のブランチを作る
   `git fetch origin main && git checkout -B claude/roundup-$(TZ=Asia/Tokyo date +%Y%m%d-%H%M) origin/main`（ブランチ名に時刻まで入れる。同じ日にやり直したとき、前の名前のブランチが残っていても、ぶつからないように。GitHub のブランチは Claude の環境からは消せない）
2. 対象を出す: `python3 scripts/claude_roundups.py list`
   - `status` が `ready` 以外（`not_finished`・`already_written`・`too_few_items`）なら、**何も変更せず、PRも作らずに終了**（理由を報告）
   - 出力には作品タイトルを含めません（出演者・メーカー・形式・発売日・収録時間・ジャンル（サイトのジャンルのページの一覧にあるものだけ）・デビュー作か・新着の人気順の最高順位だけ）。週の集計（本数・日別・メーカー・出演者・形式）も出ます
   - `trend` に傾向の数字が出ます: `total`・`prev_total`（前の週の本数）・`vr`・`prev_vr`・`debut`（デビュー作の本数）・`genres`（ジャンルごとの `count` と前の週の `prev`）・`popular`（この週に発売された作品の、新着の人気順の最高順位 `best`・その日 `best_date`・10位以内の日数 `days10`・100位以内の日数 `days100`・メーカー・出演者。過去作品の作品も入る）・`popular_ranked`（人気順に入った作品の数）・`popular_makers`（上位10本に2本以上あるメーカー）
3. 下の「書き方」に沿って、記事を書き、次の形のJSONファイルにする（作業用の置き場に。リポジトリには入れない）
   ```json
   {"week_start": "listに出た週の月曜日", "lead": "導入文", "trend": "この週の傾向", "picks": [{"cid": "作品ID", "note": "ひとこと"}]}
   ```
4. 点検して書き込む: `python3 scripts/claude_roundups.py apply ファイル.json`
   - 先に `--dry-run` で点検してもよい。問題があると**何も書き込まれず**、理由が出る。直してもう一度実行する
5. `bash scripts/check.sh` を実行して全部成功することを確認する
6. `git status` で、変わったのが **`site/src/data/roundups.json` だけ**であることを確認する。他のファイルが変わっていたらコミットしない
7. コミット → ブランチをpush → PRを作る（`gh api repos/juice0402/fanza-ranking/pulls`。CLAUDE.md の守ること1・2）
   - コミットメッセージ: `週のまとめ記事を追加（Claude）: 2026年9月28日〜10月4日`（データだけのPRなので、プレビューは作られない。待つのは CI（check）だけ。Cloudflare のビルドは使わないので、`[CI Skip]` は要らない）
   - PRのタイトル: `週のまとめ記事を追加（Claude）: 2026年9月28日〜10月4日`
8. CIが終わるまで待つ（`gh api repos/juice0402/fanza-ranking/commits/<ブランチの先頭>/check-runs` で `conclusion` を見る。数分）
   - **緑ならMerge**（`gh api -X PUT repos/juice0402/fanza-ranking/pulls/<番号>/merge -f merge_method=merge -f sha=<先頭> -f commit_title="Merge #<番号>: 週のまとめ記事を追加（Claude）: 2026年9月28日〜10月4日" -f commit_message=""`。Merge すると、公開（`deploy.yml`）が自動で動く）
   - 赤・時間切れ・衝突（Mergeできない）のときは**Mergeしない**。PRを開いたまま、理由を報告して終了する。衝突のときは、ブランチを捨てて手順1からやり直してよい（1回だけ）
9. Merge したら、公開（Deploy）が終わるのを待ってから（ビルド・点検・アップロードで10〜15分。`gh api "repos/juice0402/fanza-ranking/actions/workflows/deploy.yml/runs?branch=main&per_page=3" --jq '.workflow_runs[] | .status + " " + (.conclusion // "") + " " + .head_sha[0:7]'` が、Merge のコミット（かそれより新しいもの）で `completed success`。`cancelled` は、あとの公開に含まれたということ）、本番の `https://fanza-ranking.pages.dev/weekly/<週の月曜日>/?cb=日時` を WebFetch で見て、記事が出ているかを確認する（`?cb=` を付けないと古い内容が返ることがある）。見られなかったら「未確認」と書く
10. 最後に報告する: どの週の記事か／PR番号／CIの結果／Mergeしたか／本番で確認できたか

Mergeしてよいのは、**このまとめ記事のPR（`roundups.json` だけを変えるもの）で、CIが緑のとき**だけです（運営者の包括的な許可にもとづく。CLAUDE.md の守ること1）。

## 書き方

コメントの書き方（`docs/claude-comments.md`）と同じ考え方です。`apply` が点検するので、違反するとはじかれます。

使ってよい情報は、**`list` に出たもの（出演者・メーカー・形式・発売日・収録時間・週の集計）だけ**です。作品タイトルは見えません（見ないで書きます）。

### 導入文（lead）

- 80〜300文字。「です・ます」調で、読んだ人がこの週の新作を見てみたくなる、前向きなトーン
- その週に当サイトで何本紹介したか、どの日に多かったか、メーカーや出演者の目立った動き（本数）、VR・8K などの形式があったこと、を事実で書く
- **本数は「当サイトで紹介した◯本」「掲載した◯本」と書く。** 「発売された新作は全部で◯本」「◯日に◯本発売」のように、FANZA全体の発売本数であるかのようには書かない（当サイトは、毎日の更新で新作の一部を紹介しているだけで、`list` の本数はその数のため。日ごとの本数も、更新1回の紹介数の上限に左右される）
- 数字は、`list` に出た数字（本数・日付・収録時間）だけを使う（ほかの数字が入ると `apply` が断る）
- 期間は日付で書く（例: 「9月28日から10月4日に」）。**「今週」「先週」「今日」など、日がたつと古くなる言い方は使わない**（記事は残り続けるため。使うと `apply` が断る）
- 作品の中身（ストーリー・内容・演出）、出演者の経歴・容姿・人気の評価、ランキングのような言い方（「No.1」「人気」）は書かない（確かめられないため。人気順の数字のことは、下の「この週の傾向」に、数字を添えて書く）
- 過激・直接的な表現、性的な描写、未成年を連想させる言葉は使わない
- 挨拶・絵文字・飾りの記号・マークダウン・URLは入れず、本文だけ。改行も入れない

### この週の傾向（trend）

- 80〜360文字。導入文と同じ「です・ます」調・同じルール（古くなる言い方・使えない言葉・URL・絵文字・改行は不可）。導入文と同じ文にしない
- **`list` の `trend` の数字から読み取れることを、数字を添えて書く**: 前の週より本数が増えた・減った（「前の週の18本から6本増えて24本」）、ジャンルの増減（「人妻・主婦が前の週の2本から7本に」）、VR作品の割合、デビュー作の本数、新着の人気順で上位に入った作品の傾向（「最高1位まで上がったのは〇〇の作品で、10位以内に4日入りました」「上位10本のうち3本が〇〇」）
- 「考察」は、数字から言えることだけにする（「〇〇のジャンルが増えた週」「上位はVR作品が多い」など）。**理由の推測（「〜だから人気」）・確かめられない評価（「話題」「大人気」「待望」「圧倒的」など。`apply` が断る）は書かない**。人気順の数字があるので「人気の」「注目の」は使ってよい
- 人気順の数字は「新着の人気順で最高○位」のように、何の順位かを書く（FANZA全体の売上の順位ではない）。人気の記録が無い週（`popular` が空）は、本数とジャンルの比べだけで書く
- 使ってよい数字は、`trend` に出た数字（本数・前の週の本数・その差・ジャンルの本数と差・順位・日数・最高順位の日付）と、導入文で使える数字（ほかの数字は `apply` が断る）。「10位以内」「100位以内」の10・100も使える

書き方の例（名前・数字は仮のもの）:

- trend: 前の週の18本から6本増えて、24本を掲載しました。ジャンルでは人妻・主婦が前の週の2本から7本に増え、VR作品は8本と前の週並みです。新着の人気順では〇〇の作品が最高1位まで上がり、10位以内に4日入りました。上位10本のうち3本が△△の作品で、デビュー作も2本が100位以内に入っています。

### 注目の作品（picks）とひとこと（note）

- 3〜6本。**この週に発売された作品の `cid` だけ**。同じ作品を2回入れない。**`no_pick: true` の作品は選ばない**（未成年を連想させるタイトルの作品。こちらから勧める欄のため。`apply` が断る。サイトも出さない）
- 選び方の目安（すべて `list` の事実から）: 新着の人気順の最高順位（`best_rank`）が高い・デビュー作（`debut`）・発売日がばらける・メーカーがばらける・VR や 8K などの形式がある・収録時間が分かる・出演者の名前がある。タイトルや内容で選ばない（サイトは、注目の作品に「新着の人気順 最高○位」「デビュー作」の札を自動で付ける）
- ひとことは40〜120文字。その作品の `list` の情報（出演者・メーカー・形式・発売日・収録時間）だけで、1本ごとに書き出しと言い回しを変える。同じ文を使い回さない
- 出演者名は入れてよい（1回まで）。収録時間は「約120分」のように事実だけ。「長い」「短い」などの評価はしない
- 上の導入文と同じ、使えない言葉・言い方のルールがそのまま当てはまる

書き方の例（名前・数字は仮のもの）:

- lead: 9月28日から10月4日に発売された新作のうち、当サイトで紹介したのは24本でした。掲載が多かったのは10月3日で、6本が並びました。メーカーでは〇〇が3本、△△が2本と続き、VRや8Kの作品も含まれています。気になる作品は、詳細ページからFANZAの公式情報を確かめてみてください。
- note: 〇〇さん出演の、△△が贈るVR作品です。10月2日の発売で、収録時間は約120分。臨場感のある映像を楽しみたい方にチェックしてほしい一本です。

## うまくいかないとき

- `apply` が断ったとき: 表示された理由（文字数・使えない言葉・一覧にない数字・同じ文の使い回し など）を直して、もう一度実行する
- `list` の `status` が `ready` でないとき: 何もしないで終了する（記事がない週があっても、サイトは壊れない）
- CIが赤いとき: Mergeせず、PRを開いたまま報告する（運営者がClaudeに相談する）
- リポジトリに入れない／PRを作れないとき: 無理に回り道をせず、できなかった理由を報告して終了する。データは壊れていないので、翌週に前の週の分もまとめて書けるよう、`list --week-start 月曜日` で過去の週を指定してやり直してもよい
- 抜けた週の記事は、あとから `list --week-start YYYY-MM-DD`（月曜日）で書ける（1回の実行で1本）
- 傾向の無い前の記事（2026-10-07 より前に書いた記事）には、`add-trend` で傾向だけをあとから足せる（`{"week_start": "...", "trend": "..."}`。導入文・注目の作品・公開日は変えない。点検は apply と同じ）
